# dashboard4servers

複数のサーバー環境（PLM）の情報を1か所で管理する仕組みを、**SharePoint の標準の機能だけ**で作る。

このファイルは引き継ぎの入口である。**担当する者は、まずこれを読む。**
決まったことは変えない。決まっていないことは、案件の責任者に聞く。

## このレポジトリについて

**公開レポジトリである。**実装する端末から git が使えず、ブラウザだけが届くため、
貼り付け用の JSON をブラウザで開いて写す形にしている。

- **組織名・人名・拠点名・ホスト名・製品名は、すべて伏せてある。**`AA` と `BB` は組織、
  `作業者` と `運用担当` は担当者を指す
- **見本の中の値と日付は、すべて仮のものである。**実在の設定ではない
- **実名を書かない。**書き足すときも伏せた表記のまま書く

作成＝2026-09-03。

## 1. 何を管理するのか

- 環境ごとの用途・接続先・制約・条件
- 構築の途中で起きたトラブルと、その後の改修
- 構成図やスクリーンショットの画像
- 出来事の時系列

現状は表計算ソフトで管理しており、画像と時系列の管理が破綻している。

## 2. 制約（これは動かせない）

- **新しい SaaS を導入できない。**セキュリティ上の制約である
- **外部サービスを API キーで使うことができない**
- **サーバーを新しく立てられない**
- **実装する端末に、新しいソフトを入れられない**
- **その端末から git が使えない。**ブラウザだけが届く
- 既に社内にあって使えるもの＝**SharePoint**（確認済み）
- Power Automate と Power Pages も使える状態にあるが、**今回は使わない**（理由は6節）

## 3. 決まった構成

**リストを2つ作り、1つのページに並べる。**

| 何を | どこに置くか |
|---|---|
| 環境の「いまの状態」 | リスト **環境台帳**（1行＝1環境） |
| トラブル・改修の「経緯」 | リスト **対応の経緯**（1行＝1件） |
| 2つのつなぎ | **参照（Lookup）の列。**対応の経緯から環境台帳の環境IDを選ぶ |
| 見た目 | **標準のページに、Webパーツを6つ並べる**（うち3つがリスト） |
| 画面の作り込み | **列とビューとフォームの書式設定（JSON）。**追加の承認が要らない範囲に限る |
| 機密（パスワード等） | **今回は作らない。**どの列にも書かない |

### なぜ2つに分けるのか

環境の一覧は、上書きされ続ける「今」である。並べ替えたり絞り込んだりして使う。
トラブルと改修は、消してはいけない「過去」の積み重ねである。時系列に読む。
**この2つを1つの表に入れると、どちらかが必ず使いにくくなる。**表計算ソフトが破綻したのもこれが原因である。

### 環境IDの規則

- `ENV-001` から始まる通し番号にする
- **意味を持たせない。**組織名やシステム名を含めない
- **一度振ったら変えない**
- 理由＝**環境名は今後変わる可能性がある**と案件の責任者が明言している。名前を含んだIDにすると、名前が変わったときに全部を直すことになる

### つなぎ方

- 対応の経緯の「環境ID」は**参照（Lookup）の列**にし、環境台帳から選ばせる
- **テキストで書き写させない。**書き間違えると、その1件が行方不明になる
- 環境台帳の側から「この環境の経緯は何件か」を出すことはできない。
  **リストをまたいだ集計ができないため、**件数は対応の経緯のグループの見出しに出す

### 機密を作らない

**パスワード・秘密鍵・証明書を、どの列にも書かない。**理由は3つある。

1. **SharePoint に列単位の権限が無い。**その行を見られる者は、その列も見られる
2. **バージョン履歴に残る。**一度書くと、消しても前の版に残る
3. **持ち出される。**リストの内容は表計算ソフトに書き出せる

保管の仕組みそのものは、今回は作らない（2026-09-03 の判断）。

## 4. 名前の決めごと

**リストと列は、英数字の名前で作ってから、表示名を日本語に変える。**

理由＝**作ったときの名前が、そのまま URL と内部名になる。**あとで表示名を変えても内部名は変わらない。
日本語で作ると、内部名が `_x74b0__x5883_` のような記号の並びになり、
**書式設定の JSON から列を指せなくなる。**

内部名の一覧は `docs/010_リストの列定義.md` にある。

## 5. 時系列をどう出すか

**対応の経緯のリストに、ビューを1つ作る。**リストの書式設定（JSON）で、1行を1本の帯にする。

- 帯の左の位置と長さを、**発生日と完了日から計算する**
- 期間は**今日の90日前から60日後まで**の150日で固定する。だから今日は常に60%の位置になる
- 環境IDでグループ化し、**グループの見出しに目盛りと件数を出す**
- 帯にカーソルを当てると、内容と対応したことがカードで出る

貼り付ける JSON は `json/3_対応の経緯_ビュー_時系列.json` である。

## 6. 使わないものと、その理由

| 使わないもの | 理由 |
|---|---|
| Redmine | **情報が2か所に散る。**入力する場所が2つあると、片方だけが新しくなる。時系列は対応の経緯のビューで出せる |
| Power Apps | 標準のページと書式設定で足りるか確かめる前に手を出すと、ライセンスの確認で止まる |
| SPFx（独自の部品の開発） | テナントへの配置に管理者の承認が要る |
| Power Automate | 承認と設定が要る。**今回の作業には入れない** |
| Power BI | 共有に有償のライセンスが要る |
| Power Pages | 社外向けのウェブサイトを作る道具である。用途が合わない |
| クイック チャートのWebパーツ | **手で数字を入れる部品で、リストと連動しない。**古い数字が画面に残る |
| ローカルの LLM | 端末に導入できない |

**すべて、標準のリストと書式設定から始める。**理由＝データがリストにある限り、
後から別の画面へ移してもデータを作り直す必要がない。**上に載る画面だけが変わる。**

## 7. 見本（完成したときの姿）

`mock/ダッシュボード見本.html` をブラウザで開く。**触れる。**
カードの「詳細」「編集」、行の「···」、帯、状態の札を押すと、実物と同じ形のパネルが出る。

**説明用の見本であって、実装ではない。**中の値と日付はすべて仮のものである。
画面のどの部分をどの機能で作るのかは、見本の下の表に書いてある。

## 8. 作業の進め方

**実装は作業者が行う。**指示は指定のチャネル経由で出す。以下は案件の責任者の指定である。

1. **会話するチャネルは1つに限る。**他の話題と混ざるのを避けるためである
2. **作業者は SharePoint に詳しくない。**画面のどこを押すのかまで書く
3. **推測で手順を書かない。**製品の公式文書で裏を取ってから出す
4. **作業者はチャネルを個人の携帯で読む。**実装は貸与された端末で行う。
   → **携帯で読める長さと形にする。**長い表を貼らない
5. **関係者への確認は今はしない。**空欄のまま作る。埋まらない欄が、あとで聞くことの一覧になる

### JSON の渡し方

貸与された端末から git が使えないため、**ブラウザで写す。**

1. `json/` の中から、貼り付け先のファイルを開く
2. **「Raw」を押す。**通常の画面には行番号が付くので、そのままでは壊れる
3. 全部を選んでコピーする
4. SharePoint の設定欄に貼って、保存する

## 9. 次の一手

1. `steps/手順.md` の順に、リストを1つ作ってもらう
2. 列を作り、表示名を日本語に変える
3. JSON を5か所に貼る
4. ページを作り、Webパーツを並べる

